# CORE-002A Root-Cause Checkpoint

Baseline: TEST-003 10,000 cases, seed `12345`, head `8b76a50b54fb1788ba1658ef0cefc19090b17ddc`.

## Stop-condition finding

Before changing production Core, the baseline `report.json` was reclassified by geometry subcheck and by the exact dimension-line evidence generated by `DimensionCasePrimitiveSceneBuilder`.

All **3,454** TEST-003 `WrongGeometry` cases contain a `dimension-line location` failure. Only **20** contain a wrong `extension-line point 1`, **16** contain a wrong `extension-line point 2`, and **1** contains a broken-line provenance mismatch.

For non-chain positive cases the TEST-003 builder deterministically constructs the supplied dimension line from noisy P1/P2, angular skew and noisy dimension-line offset. Production Core currently reconstructs `DimensionLinePoint` as the midpoint of the selected dimension-line primitive. Recomputing that exact builder midpoint from the frozen TEST-003 inputs shows:

- **3,384 / 3,454** `WrongGeometry` cases: Core's returned `DimensionLinePoint` is byte/numerically identical (<= 1e-9 paper units) to the midpoint of the full dimension-line evidence generated by TEST-003.
- **3,353 / 3,454** cases (97.08%): `dimension-line location` is the **only** wrong geometry subcheck even though Core returns the exact midpoint of the selected full dimension line.
- another **31** cases have the same dimension-line trace/invariant conflict plus an endpoint reconstruction issue.
- **50** regular positive cases are materially different: Core provenance contains only `:dimline:left` or only `:dimline:right` for a micro-broken dimension line instead of merged evidence. These are genuine production broken-line selection repros.
- **20** remaining cases are chains and require a separate chain-specific invariant analysis.

The current TEST-003 `SceneTraceBuilder.FindDimensionLineLocation` does **not** record the midpoint of the supplied dimension-line primitive. It projects the clean expected `DimensionLinePoint` onto the noisy input line. `ErrorClassifier` then compares the Core midpoint to that projected point using Euclidean point error. Under coordinate jitter, both points lie on the same dimension line and therefore encode the same dimension-line placement/offset, but their along-line coordinates differ. This turns permitted injected along-line movement into `WrongGeometry`.

This is significant enough to trigger the CORE-002A stop condition. No production Core geometry change should be justified by the 3,353 cases until the diagnostic invariant is resolved explicitly. TEST-003 tolerance has not been changed.

## Endpoint note

The first large endpoint repro is `case_000023` (`uneven-extension-lines`). Current `DefinitionPoint(extension, dimensionLine)` chooses whichever extension endpoint is farther from the dimension line. When the overrun past the dimension line is intentionally longer than the distance back to the measured point, this selects the wrong side. However, without additional object-geometry evidence the two endpoints can be visually ambiguous, so this case must not be used to change production Core until a non-ambiguous endpoint invariant is proven.
