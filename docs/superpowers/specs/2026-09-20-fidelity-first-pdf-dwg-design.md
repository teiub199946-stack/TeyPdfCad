# Fidelity-first PDF → DWG: проектное решение

## Цель

Сначала получить детерминированный редактируемый DWG, визуально максимально
близкий к исходному векторному PDF, и только затем возвращать нативную CAD-
семантику. Внешняя точность и семантическая реконструкция рассматриваются как
два независимых этапа с отдельными метриками и приёмочными гейтами.

Контрольный материал первого блока — страница 29 `Aidyn.pdf`. Её данные служат
регрессионным fixture, но особенности страницы не должны попадать в production-
логику.

## Основные принципы

- `Fidelity` никогда не распознаёт и не заменяет исходные объекты.
- `Review` добавляет распознанные объекты, но не удаляет источник.
- `Semantic` заменяет только валидированные целые объекты с достаточной
  уверенностью.
- Структурная метрика первична. Растровая метрика вторична и учитывает
  различия рендереров.
- Любая гипотеза о возможностях ACadSharp/AutoCAD сначала доказывается отдельным
  spike через цикл `write → save → reopen → AutoCAD render`.
- Нельзя заявлять визуальное исправление только по счётчикам сущностей или
  read-back.

## Обязательные предварительные spike

### Spike A: управление draw order

Создаётся минимальная сцена:

1. цветная геометрия;
2. перекрывающая белая заливка;
3. текст поверх заливки.

Сравниваются:

- обычный порядок добавления сущностей;
- явный draw-order / `SortEntitiesTable`, если поддерживается writer-ом;
- результат после сохранения и повторного открытия;
- результат AutoCAD-рендера после повторного открытия.

Первый практический артефакт проекта:

```text
spike-draw-order-report/
  fixture.*
  insertion-order.dwg
  explicit-order.dwg
  reopened-*.json
  rendered-*.png
  report.md
```

Spike завершён только при однозначном доказательстве механизма, который
стабильно сохраняет порядок после `save → reopen → render`. Если ни один
механизм не работает, это фиксируется как блокер Fidelity writer-а.

### Spike B: ширина нативного текста

Для горизонтального и повёрнутого на 90° слова создаются три варианта:

1. обычный `TEXT`;
2. `TextHorizontalAlignment.Fit` между началом и концом baseline;
3. калиброванный `WidthFactor`.

Проверяются:

- начало и конец baseline;
- ориентированный bbox/quad;
- высота;
- угол;
- порядок символов;
- результат после read-back;
- AutoCAD render.

Предварительные гейты:

- ошибка baseline endpoints не более `0,2 мм`;
- acceptance-ошибка высоты не более большего из `5%` и `0,15 мм`;
- целевая ошибка высоты после font-mapping не более `3%`;
- ошибка угла не более `0,1°`;
- символы не переставлены и не разорваны;
- mask IoU слова не менее `0,90` для горизонтального и `0,85` для
  повёрнутого текста после допуска антиалиасинга.

Пороги могут быть скорректированы только отчётом spike, если различие PDF-
шрифта и `arial.ttf` делает исходные значения недостижимыми. Если все три
варианта провалены, фиксируется отдельный блокер `font-mapping`; худший вариант
не выбирается молча.

Spike B выбирает глобальный механизм записи нативного текста. Конкретные слова
после этого проверяются structural diff по baseline, quad, высоте, ширине и
повороту; каждое слово не проходит Spike B повторно.

### Spike C: взаимный порядок текста и графики

Текущий reader получает геометрию из `PdfGraphicsOperationInterpreter`, а
`VectorText` добавляет отдельным проходом по `sourcePage.Letters` после
завершения интерпретации. Поэтому реальный interleaving `text ↔ fill ↔ stroke`
сейчас уже утрачен.

Spike C должен определить, можно ли:

1. извлекать text-show операции из `sourcePage.Operations` вместе с графическими
   операциями и присваивать единый `PaintOrder`;
2. надёжно сопоставлять эти операции с декодированными `Letter`/`Word`;
3. сохранять порядок для текста с вложенными graphics state, transform и clip.

Обязательные fixtures:

- обычный текст между stroke/fill операциями;
- несколько text-show операций, образующих одно слово;
- вложенные `q/Q`;
- text matrix и поворот;
- активный clip;
- прерывание слова графической операцией.

Критерий успеха:

- `100%` text-show операций synthetic fixtures однозначно сопоставлены с
  декодированными символами/словами;
- нет противоречий порядка;
- повторный запуск создаёт идентичный mapping;
- для страницы 29 отчёт содержит долю сопоставленных операций и полный список
  несопоставленных.

Неоднозначный synthetic mapping означает провал глобальной стратегии. Частичное
сопоставление реального листа не выдаётся за полный `PaintOrder`: для
несопоставленных объектов применяется `TextOrderingStrategy`.

Если единый поток восстановить нельзя, Fidelity использует честный fallback:

- графические сущности сохраняют доказанный `PaintOrder`;
- текст получает отдельную `TextOrderingStrategy`;
- стратегия и её ограничения указываются в отчёте;
- результат не называется точным воспроизведением PDF-порядка.

Полный `PaintOrder` для текста не добавляется в production-контракт до успешного
Spike C.

## Режимы конвертации

### Fidelity

- никакого семантического распознавания;
- никакой замены исходной геометрии;
- исходные стили, координаты и порядок рисования;
- нативный `TEXT` только там, где он проходит гейты;
- явный fallback для clipping и неподдерживаемых объектов;
- подробный provenance и диагностика.

### Review

- Fidelity-геометрия полностью сохраняется;
- кандидаты `DIMENSION`, `LEADER`, `AXIS`, `LEVEL` добавляются на
  `TEY_REVIEW_*`;
- конфликтные области выделяются отдельно;
- исходные фрагменты не удаляются.

### Semantic

- каждый тип семантики включается отдельным флагом;
- заменяются только подтверждённые целые объекты;
- low-confidence и неполные объекты остаются Fidelity-геометрией;
- включение каждого типа проходит structural и raster no-regression gate.

## Минимальный provenance-контракт

Контракт окончательно фиксируется после трёх spike, но его требуемая семантика
следующая.

### Общие поля emitted-сущности

```text
SourceId
PageNumber
PaintOrder: long
SourceOperationIndex: int
SourcePaintOperation
EmittedRole
ClipStateId?
ClipResolution
Style
Confidence
```

`PaintOrder`:

- уникален и монотонен внутри страницы;
- присваивается при эмуляции потока PDF для сущностей, участвующих в общем
  потоке;
- не пересчитывается после распознавания;
- задаёт порядок Fidelity-записи.

Для текста это требование вступает в силу только после успешного Spike C.
До этого используется явная `TextOrderingStrategy`, а отчёт не скрывает потерю
interleaving.

`SourceOperationIndex` хранит происхождение. Несколько emitted-сущностей могут
происходить из одной PDF-операции.

`SourcePaintOperation` описывает PDF-операцию, например `Fill`, `Stroke`,
`FillAndStroke`, `EOFill`, `EOFillAndStroke`, `Text`, `Clip`.

`EmittedRole` описывает конкретный результат: `Fill`, `Stroke`, `Text`,
`ClipArtifact` или `Fallback`.

Для операции `FillAndStroke` создаются как минимум две emitted-сущности с
разными `PaintOrder` и `EmittedRole`.

## Clipping

Контракт не обещает нативно перенести произвольный PDF clip в DWG.

### Clip provenance

Отдельная таблица состояния:

```text
ClipStateId
SourceOperationIndex
IsActive
Regions
```

Она нужна для аудита, воспроизведения решения и диагностики.

### Результат разрешения

```text
ClipResolution:
  Unknown
  Unclipped
  Flattened
  Native
  OutlineFallback
  ReviewOnly
  Unsupported
```

Правила:

- до появления `ClipProvenance` объект получает `Unknown`, а текст —
  `ReviewOnly`, если отсутствие влияния clip не доказано;
- линии и полилинии предпочитают `Flattened`;
- заливки предпочитают `Flattened` с сохранением fill rule и внутренних
  границ;
- полностью видимый текст остаётся `Native`;
- частично обрезанный текст использует `OutlineFallback` или `ReviewOnly`;
- растровый fallback допустим только как явно отражённое исключение;
- `Unknown` и `Unsupported` всегда попадают в обязательный реестр артефактов,
  считаются по зонам и не маскируются показателем общей успешности.

## Текстовый контракт

Для каждого слова хранятся:

```text
BaselineStart
BaselineEnd
WordQuad
GlyphHeight
AdvanceWidth
Rotation
SourceFontId
```

`WordQuad` — ориентированный четырёхугольник. Axis-aligned bbox допустим только
как производная метрика и не заменяет quad для повёрнутого текста.

`SourceFontId` — диагностический ключ. Он не означает, что PDF-шрифт будет
встроен или доступен в AutoCAD.

Уже реализованные `GlyphHeight` и rotation-aware `AdvanceWidth` сохраняются.
Выбор между `Fit`, `WidthFactor` и font-mapping определяется только Spike B.

## Заливки и порядок

Белые заливки не удаляются по цвету. Они могут быть:

- фоном;
- частью векторного глифа;
- knockout-mask;
- обычной чертёжной заливкой;
- ошибочно реконструированной compound path;
- настоящим дубликатом.

Удаление допустимо только для доказанного дубликата с совпадающими:

- геометрией и трансформацией;
- цветом и прозрачностью;
- fill rule;
- clip state;
- ролью и положением в paint order.

Простая схема `fills → geometry → text` не считается эквивалентом PDF. Главным
источником порядка является `PaintOrder`; роль используется для диагностики и
осознанных fallback.

### Известный дефект fill rule

Reader различает `NonZero` и `EvenOdd`, но текущий DWG writer добавляет все
loops как одинаковые `Hatch.BoundaryPath` и не применяет `VectorFillRule` при
настройке HATCH. Поэтому наличие значения `EvenOdd` во внутренней модели ещё не
доказывает корректный DWG-рендер. Дефект входит в Fidelity convergence и
проверяется отдельным fixture с внешним контуром и отверстием.

## Golden acceptance: страница 29

### Source baseline v0

Фиксируется сразу только из полей, уже доступных в текущем reader-контракте:

- число сущностей по типам;
- координаты и стили;
- `InsertionPoint`, высота, `AdvanceWidth` и поворот текста;
- границы, площадь, fill rule и clip заливок;
- unsupported diagnostics.

`BaselineStart/End` и `WordQuad` не входят в v0: текущий `VectorText` их не
содержит. Они добавляются только в подтверждённый provenance-контракт после
spike и входят в v1.

### Source baseline v1

После Spike A–C и реализации минимального provenance-контракта добавляются:

- `PaintOrder`;
- `SourceOperationIndex`;
- `SourcePaintOperation` и `EmittedRole`;
- `ClipProvenance` и `ClipResolution`;
- `TextOrderingStrategy`, если единый порядок текста не восстановлен.

### Structural diff

Проверяет:

- потерянные, добавленные и изменённые сущности;
- линии по endpoints, углу и длине;
- текст по baseline, quad, высоте, ширине и углу;
- заливки по площади, контурам, fill rule и порядку;
- clipping и fallback;
- source → DWG provenance.

Для тонких линий используется matching endpoints/angle/length и
distance-transform/chamfer. Голый IoU не является основной метрикой.

### Raster diff

- фиксируются версии PDF- и AutoCAD-рендереров, DPI, фон, цветовой профиль,
  lineweight/display settings и параметры plot;
- PDF и DWG рендерятся при одинаковом DPI и размере canvas;
- контрольный DWG рендерится минимум дважды в одном окружении;
- run-to-run diff фиксируется как baseline шума рендерера;
- приёмочные пороги не могут быть меньше измеренного baseline шума;
- изображения регистрируются по рамке листа с сохранением матрицы
  преобразования и ошибки регистрации;
- допускается морфологическая терпимость `1–2 px`;
- метрики считаются отдельно по зонам: чертёж, размеры, текст, штамп, таблица;
- общий score не может скрыть провал отдельной зоны.

Зоны golden-листа задаются вручную проверенными прямоугольниками в fixture
metadata. Они не зависят от ещё отключённой семантики и не вычисляются
production-распознавателями.

Отчёт сохраняет:

- оба исходных рендера;
- зарегистрированные изображения;
- бинарные и тепловые diff-карты;
- маску допуска;
- fixture metadata;
- метрики по каждой зоне;
- параметры запуска рендереров.

Текущий неисправный DWG не становится golden. DWG golden фиксируется только
после достижения согласованного Fidelity-уровня.

## Порядок реализации

1. **Spike A: draw order.** Доказать стабильный механизм и выпустить
   `spike-draw-order-report`.
2. **Spike B: text fitting.** Выбрать `Fit`, калиброванный `WidthFactor` или
   зафиксировать `font-mapping` blocker.
3. **Spike C: text ordering.** Доказать общий порядок text/graphics либо
   зафиксировать явную fallback-стратегию.
4. **Provenance + Fidelity stand.** Реализовать только поля и clip-стратегии,
   подтверждённые spike; добавить режим без семантики, source baseline,
   structural diff и зональный raster diff.
5. **Fidelity convergence.** Исправлять текст, draw order, заливки, clipping,
   потерянные/лишние объекты только по измеримым дефектам.
6. **Semantic return.** Включать `DIMENSION`, `LEADER`, `AXIS`, `LEVEL`,
   semantic hatch по одному типу с no-regression gate.

Multi-layout выполняется после стабилизации Fidelity и не блокирует первый
контрольный лист.

## Парный протокол работы

- Один участник реализует изолированный шаг.
- Второй независимо проверяет предположение, diff, тесты, DWG read-back и
  AutoCAD render.
- Автор не принимает собственную правку в одиночку.
- Роли меняются между этапами.
- Один и тот же файл параллельно не редактируется.
- После каждого завершённого изменения выпускаются:
  - отдельный DWG или fixture;
  - численная метрика;
  - перечень исправленного и оставшегося;
  - SHA;
  - независимое заключение проверяющего.

## Что запрещено

- внедрять полную provenance-модель до трёх spike;
- считать insertion order доказанным без save/reopen/render;
- удалять белые заливки только по цвету;
- калибровать `WidthFactor` вслепую;
- выдавать частично clipped `TEXT` за точный нативный объект;
- использовать axis-aligned bbox как основной bbox повёрнутого текста;
- считать raster diff единственной метрикой;
- включать семантику до сходимости Fidelity;
- хардкодить особенности страницы 29;
- начинать multi-layout раньше Fidelity;
- заявлять готовность по счётчикам сущностей без визуальной проверки.

## Критерий успеха первого блока

Первый блок завершён, когда:

- все три spike имеют воспроизводимые отчёты;
- Fidelity-режим не содержит семантических замен;
- порядок и clipping имеют явный, проверяемый результат;
- страница 29 проходит structural и зональные raster-гейты;
- каждая зона проходит зафиксированные пороги;
- все оставшиеся white-fill и text-overlap артефакты перечислены в отчёте,
  привязаны к source provenance и имеют объяснённый статус;
- результат независимо проверен вторым участником;
- только после этого разрешено возвращать первый тип семантики.
